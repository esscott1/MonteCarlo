# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

A Monte Carlo retirement-portfolio simulator: given an investment scenario, a starting balance, and an annual withdrawal, it runs many randomized simulations of portfolio performance over a number of years and reports survival rate and balance outcomes. Available as both a console app and a web GUI, both built on .NET 9 and sharing one simulation engine.

## Goal

**Maximize the spending that survives 80–85% of simulated markets for the given inputs.** Every model choice about which account pays for spending or taxes — the withdrawal order, where a Roth conversion's tax comes from — is made by the app to serve that goal and measured with the Strategy Lab (below); users don't choose it. When a change touches those choices, rerun the lab and let its numbers decide. The Model Info page shows the current measurements.

## Commands

```bash
# Build everything
dotnet build MonteCarlo.sln

# Build a single project
dotnet build MonteCarloSimulation.Core/MonteCarloSimulation.Core.csproj

# Run the console app (interactive prompts)
dotnet run --project MonteCarloSimulation1

# Run the web app, then open http://localhost:5091
dotnet run --project MonteCarloSimulation.Web

# Run the automated tests
dotnet test MonteCarlo.sln

# Run the Strategy Lab (long: ~40 minutes on 12 cores for the full 1,000 scenarios; --quick runs 50).
# --set funding compares where conversion tax comes from; run it before the main set's --publish so the
# Model Info page includes it. Rerunning finished settings with the same engine resumes in about a minute.
dotnet run -c Release --project MonteCarloSimulation.StrategyLab -- --set funding
dotnet run -c Release --project MonteCarloSimulation.StrategyLab -- [--quick] [--scenarios 1000] [--paths 200] [--seed 2026] [--publish]
```

`MonteCarloSimulation.StrategyLab.Tests` self-checks the Strategy Lab harness (its app combinations and funding rules run exactly like `MonteCarloEngine.Run`, candidate orders stay within balances and the age gate and net the need, seeds reproduce, the published Model Info data matches the current `Summary`). `MonteCarloSimulation.Optimizer.Tests` covers the Optimal page's optimizer (curve, percentile band, break-even search, end-to-end survival band and repeatability). `MonteCarloSimulation.Core.Tests` has two layers. `MonteCarloEngineTests` covers `MonteCarloEngine`'s run-outcome behavior end to end (all-succeed, all-fail, statistically-approximate pass rates, and deterministic `StdDev = 0` scenarios for strategy order, the age gate, conversions and Social Security). `ComponentTests` pins exact values for the internal building blocks (`TaxYear`, `Accounts`, the withdrawal strategies, `RothConversion`, `SocialSecurityYear`), which Core exposes to the test project via `InternalsVisibleTo`. Beyond that, verification has been manual: smoke-running the console app with piped stdin input, and exercising the web app live in a browser.

**Windows gotcha:** if a previous `dotnet run` of `MonteCarloSimulation1` or `MonteCarloSimulation.Web` wasn't cleanly exited, its `.exe` stays locked and the next `dotnet build`/`dotnet run` fails with `MSB3021`/`MSB3027`. Kill the stray process (`Get-Process MonteCarloSimulation1,MonteCarloSimulation.Web -ErrorAction SilentlyContinue | Stop-Process -Force`) before rebuilding.

## Git branch hygiene

**Standing procedure once a PR has been merged** — do this without being asked whenever the user says a PR merged (or you see that it has):
1. Confirm it really merged: `gh pr view <number> --json state,mergedAt` shows `MERGED`.
2. Switch to `master` and fast-forward it: `git switch master && git pull --ff-only`.
3. Confirm the branch is contained in `master`: it appears in `git branch --merged master`.
4. Delete the remote branch (GitHub doesn't auto-delete it in this repo): `git push origin --delete <branch>`.
5. Delete the local branch: `git branch -d <branch>` (lowercase `-d`, which refuses unmerged work — never `-D`).
6. `git fetch --prune`, then report what was deleted and what branches remain.

Never delete a branch whose PR is still open or that isn't contained in `master` (e.g. `feature/change-request-status-spinner`, PR #22, open) — ask the user instead. The same applies to stale branches found during other branch work: `git fetch --prune`, then delete local branches whose remote-tracking branch is gone (`git branch -vv` shows `: gone]`) with `git branch -d`, confirming with the user before deleting anything that isn't obviously merged.

Source files are UTF-8 with CRLF line endings in the working copy (`core.autocrlf=true`; the repo stores LF). BOM use is mixed — most `.cs` files have none, the `.csproj` files do — so preserve each file's existing BOM state and give new `.cs` files none. `git add` will warn `LF will be replaced by CRLF`; that's expected and harmless. Note that `sed -i` in Git Bash rewrites files with LF; restore CRLF afterwards.

## Architecture

Eight projects in `MonteCarlo.sln`: the five below, plus the three test projects described above.

- **`MonteCarloSimulation.Core`** — the entire simulation engine, with zero I/O. `MonteCarloEngine.Run(SimulationParameters)` is the single source of truth for all financial math; both front ends call it and only format its output differently. Never duplicate simulation logic into either front end — if a calculation needs to change, it changes here once. Also holds `SimulationParameters`/`SimulationResult`/`SimulationRunOutput`/`RunSummary`/`RunYearDetail` (plain data) and `InvestmentScenarios` (the 4 built-in scenario presets, shared so neither front end re-hardcodes the same numbers).
- **`MonteCarloSimulation1`** — the console app. A thin I/O loop: prompt for input (`SimulationPrompt`), call `MonteCarloEngine.Run`, print results (`SimulationReporter`).
- **`MonteCarloSimulation.Web`** — an ASP.NET Core minimal API (`GET /api/scenarios`, `POST /api/run`) serving a static `wwwroot/` page (plain HTML + vanilla JS, no framework, no build step). The frontend never touches the input form when rendering results — results and inputs are separate DOM subtrees, which is what keeps inputs visible after a run.
- **`MonteCarloSimulation.Optimizer`** — the **Optimal** page's logic (`optimal.html`/`optimal.js`, `POST /api/optimal`, linked from the main page's menu). It answers the inverse question: the annual spend that survives 80–85% of simulated markets per investment scenario, and the Social Security start age (each birthday 62–70) that allows the most. Deliberately isolated from the main page: it only *calls* Core, never changes it. It needs repeatable seeded runs, so Core's `.csproj` grants it `InternalsVisibleTo`, and it runs Core's own per-run loop (`RunSimulator`, exactly what `MonteCarloEngine.Run` does per iteration). `SocialSecurityCurve` fills ages 63–69 from the user's 62/67/70 monthly amounts using SSA's adjustment shape (5/9% then 5/12% per early month, linear delayed credits). `SpendingOptimizer` reuses 500 seeded paths (path *i* = `new Random(i)`) for every spend, age and scenario, bisects each path's break-even spend to $100, and reads the 85%/82.5%/80% spends straight off the sorted break-evens; the recommended age maximizes the 82.5% spend and is re-simulated to report its real survival rate. Each claiming age also reports `TotalSocialSecurity` — every payment received from the start date to the end of the window, in actual (inflated) dollars, summed from the timeline exactly as `RunSimulator` pays it (it doesn't depend on markets). `ParametersCopy` copies `SimulationParameters` field by field — a test fails if a new property isn't copied, so add it there when extending `SimulationParameters`.
- **Model Info page** (`model-info.html`/`model-info.js`, linked from the main page's menu and from both pages' results) — renders the Strategy Lab's published results (`wwwroot/model-info/strategy-lab.json`) with the app's `styles.css`: numbers come from the JSON, the explanations around them are written in `model-info.js`. It has no API; the data changes only when someone reruns the lab with `--publish`. It includes the strategy definitions (orders, conversion policies, funding rules), where conversion tax comes from, how the app chooses its withdrawal order, and the Optimal page's defaults before and after the app took over those choices. The main page's results summary says which order the engine used (`output.withdrawalStrategy`) and the conversion-tax rule (from the parameters `/api/run` echoes back), linking here; the Optimal page shows the order behind each claiming age.
- **`MonteCarloSimulation.StrategyLab`** — a research console app, not part of either front end: does the app's Tax-optimized order (with its Roth conversion policy) actually let a household spend the most? It generates reproducible households over wide ranges (`ScenarioGenerator`, seeded) and, per household, runs every **withdrawal order × conversion policy** combination (`Candidates`: W1 Pro-rata and W2 Tax-optimized are Core's own; W3 the previous Tax-Deferred-to-22%-first order, W4 Brokerage-first, W5 Tax-Deferred-first, W6 greedy lowest-marginal-tax, built on `YearDraw`; W2nh is W2 without harvesting; conversion policies C0 none, C1 the 12% fill (`OrdinaryFillCeiling`), C2 the 22% line ignoring 0% gains, C3/C4 the tops of the 22%/24% brackets (C0/C1/C3/C4 are the app's `RothConversionTarget`s, mapped in `Candidates.AppTargets`), C5 the top of 22% but below the first IRMAA tier (lab-only unless `Analysis.ConversionChoices` finds it best for ≥3% of households and ≥+0.1% on average)) on the same 200 seeded paths. `PathRunner` is a lab-local copy of the Optimizer's break-even search (it doesn't touch the Optimizer); the yardstick is the spend at 82.5% survival, compared paired against the baseline W2+C1. At the baseline's spend it also records survival, lifetime taxes and after-tax ending wealth (Tax Deferred at 78%, Brokerage gains at 85%). `SingleYearCheck` brute-forces the cheapest Tax Deferred/Brokerage split for random single years and compares the Tax-optimized plan's tax to it. Two candidate sets (`CandidateSet`, `--set`): **main** (the grid above, under the app's current conversion-tax funding) and **funding** (Pro-rata and Tax-optimized × C1–C4 × the four `ConversionTaxFunding` rules F0–F3, plus C0, against W2+C1+F0 — the app before it chose its own funding). The main set also measures the **order choice** (`Analysis.OrderChoices`: each order under C1, and the app's per-household pick of W1/W2, against the best order per household; a rule qualifies when it's within 0.5% of the best in ≥95% of households and no household type falls short by more than 1% on average — no single order did, the per-household pick does) and the **conversion choice** (`Analysis.ConversionChoices`: the per-household pick of order and line against the best of every combination, how often each target wins, C5's adoption test, and `PickerAgreement` — the main page's own picker run on every household at its ideal spend) and runs the Optimal page's default inputs through the Optimizer before/after (`OptimalDefaults`). Output goes to `MonteCarloSimulation.StrategyLab/output/seed…-n…-p…-<set>-<fingerprint>/` (gitignored; `EngineFingerprint` hashes a few fixed runs of the set, so a change to Core's math or defaults starts a fresh run instead of resuming stale results): `scenarios.csv`, `results.csv` (appended per finished scenario — rerunning the same settings resumes), `page-default.csv`, `single-year.csv`, `summary.json`. `Analysis` computes everything the Model Info page shows (comparisons, household subsets, slices, largest gaps, the strategy definitions from `Candidates` with their 2026 dollar lines, and a `CaseStudy` traced year by year), so `--publish` just copies `summary.json` to `MonteCarloSimulation.Web/wwwroot/model-info/strategy-lab.json` (committed; a lab test fails if it no longer deserializes to the current `Summary`). Republish after any change to the lab or to Core's financial math. To test other conversion policies Core exposes a pluggable `ConversionCeiling` (`RothConversion.DefaultCeiling` is the app's) through an internal `RunSimulator.Simulate` overload, which also hands back the final `Accounts`; the app's path is unchanged (`ConversionCeilingTests` requires bit-identical runs). `Scenario.Copy` copies `SimulationParameters` field by field like `ParametersCopy` — extend both.

### Engine components (all `internal` to Core, one job each)

- **`MonteCarloEngine`** — public entry point: loops the iterations and assembles `SimulationRunOutput`. An `internal Run(parameters, Random)` overload lets tests pin the random sequence.
- **`RunSimulator`** — one run, year by year: advance the inflation indexes, draw the year's return, grow, plan the withdrawal, apply it, convert, record a `RunYearDetail`, check for failure. Returns a `RunSummary`.
- **`Accounts`** — the three balances plus the Brokerage/Roth cost basis; the only code that changes balances (returns, withdrawals with proportional basis shrink, deposits, conversions, the 59½ eligibility gate, the negative-balance check).
- **`TaxYear`** — one year's inflated standard deduction plus the ordinary and long-term capital gains bracket tables; all tax math. Ordinary: forward `OrdinaryTax`/`IncrementalOrdinaryTax`, inverse `GrossUpOrdinary`, `BracketRoom`, `Bracket22CeilingGross`. Capital gains: forward `CapitalGainsTax`/`TotalTax`, inverse `GrossUpBrokerageSale`, `BrokerageNetCapacity`, `CapitalGainsBracketRoom`, and the 0%-band helpers `ZeroRateCeilingGross`/`ZeroRateGainRoom`/`OrdinaryFillCeiling`. **`TaxAssumptions`** — the Social Security taxable fraction. **`Bisection`** — a monotone solver for the few amounts with no closed-form inverse.
- **`IWithdrawalStrategy`** — `ProRataWithdrawalStrategy` / `TaxOptimizedWithdrawalStrategy`, chosen by the public `WithdrawalStrategy` enum. Pure: take a `WithdrawalContext`, return a `WithdrawalPlan`; the caller applies it to `Accounts`.
- **`RetirementTimeline`** — lays the retirement window onto calendar tax years (see "The retirement timeline" below): each `RetirementYear`'s dates, fraction of the year, inflation factor, age, Social Security payment count and `TaxYear`. All date math lives here.
- **`RothConversion`**, **`GainHarvest`**, **`SocialSecurityYear`** — the conversion step, 0%-gain harvesting, and the year's Social Security income/tax/need/surplus.
- **`FailureTrace`** — builds the failed-run text trace (`OutOfMoneyMessage`) from the records.
### The retirement timeline (`RetirementTimeline`)

The whole model is based on `SimulationParameters.RetirementDate` (the web's **Retire On Date**): withdrawals begin on it, and the account balances entered are balances *as of* it — there is no pre-retirement simulation. The retirement window runs from `RetirementDate` to `RetirementDate.AddYears(Years)` and is laid onto **calendar (tax) years**: model year 0 is the calendar year of retirement, starting on the retirement date, and the last model year ends on its anniversary — so both are **partial** unless retirement starts on January 1 (in which case there are exactly `Years` whole years). Each `RetirementYear` carries its day-based `Fraction` of the calendar year.

- **Today's dollars.** `Withdrawal`, `SocialSecurityMonthlyAmount` and `AnnualStandardDeduction` are entered in today's dollars — the same 2026 basis as the bracket tables (`FederalTaxBrackets.Year`). Each year multiplies them (and the bracket thresholds) by `InflationFactor`, the cumulative inflation from 2026 to that calendar year: 2.5% a year through the first 20 years of retirement (including any years between 2026 and retirement), then 1%. Retiring in 2026 gives year 0 a factor of exactly 1.0.
- **Monthly in the UI, annual in the model.** The main page and console take the withdrawal **per month** and send `monthly × 12`; the Optimal page shows its spend figures per month (annual ÷ 12). `SimulationParameters.Withdrawal`, `/api/run` and `/api/optimal` all stay annual, and the year-by-year tables show each year's actual totals.
- **Partial years.** Spending is `Withdrawal × InflationFactor × Fraction`; the year's randomly drawn annual return is applied as `1 + rate × Fraction` (the reported `RateOfReturn` stays the annual draw). The standard deduction and brackets are *not* prorated — they're annual. Assumption: no wages in the retirement year, so the first calendar year's brackets and deduction are fully available to retirement income.
- **Age.** `AgeAtStart` is the exact age (day count ÷ 365.25) from `Birthdate` at each model year's start date; the 59½ gate is judged there, so turning 59½ mid-year unlocks withdrawals from the next year.
- **Social Security** is paid monthly on `SocialSecurityStartDate`'s day of the month, starting on that date; each year counts the payments falling inside it (`SocialSecurityMonths`), so the first benefit year is partial (born 7/7/1969, first payment 8/7/2031 → 5 payments in 2031). The year's benefit is `SocialSecurityMonthlyAmount × InflationFactor × payments` — inflating from today's dollars stands in for COLA. The web validates the start date to ages 62–70.
- `YearNewMoney` stays a model-year index (0 = the retirement year); `RunYearDetail` reports `CalendarYear`, `YearFraction` and `SocialSecurityMonths`, and the web labels years by calendar year with a partial-months note.

### The simulation model (`RunSimulator`)

The user supplies the starting `taxable`, `roth`, and `brokerage` balances directly — there is no hardcoded split. `InitialTaxableBalance` on `SimulationParameters` seeds `taxable` directly; `roth` and `brokerage` are each seeded from a Basis/Unrealized Gain pair (`InitialRothBasis`/`InitialRothUnrealizedGain` and `InitialBrokerageBasis`/`InitialBrokerageUnrealizedGain` respectively — each pair's sum is that bucket's true starting balance, tracked separately from year zero so the tax and age-gating math below is accurate). Every simulated year, all three buckets grow by the same randomly-drawn rate (Box-Muller transform over the scenario's mean/stddev), then a withdrawal is taken — ordered per the withdrawal strategy (see below) — from whichever buckets are currently *eligible* (see the age-gating paragraph below). Tax is modeled on the taxable and brokerage sides only:
- `taxable` uses the graduated 2026 single-filer federal bracket table (`FederalTaxBrackets.Single2026`): the first `AnnualStandardDeduction` dollars of that year's taxable-side withdrawal are exempt from tax, and only the amount above that is grossed up through `TaxYear.GrossUpOrdinary`, which walks the bracket table and inverts it exactly (each bracket is linear, so no iteration is needed) rather than applying one flat rate.
- `brokerage` sales are taxed as long-term capital gains, on the *embedded gain* portion only, at the 2026 single-filer rates (`FederalTaxBrackets.CapitalGainsSingle2026`, Rev. Proc. 2025-32): **0%** while total taxable income is at or below $49,450, **15%** to $545,500, **20%** above (thresholds inflated like the ordinary brackets). Gains **stack on top of ordinary income**: ordinary income (taxable Social Security, Tax Deferred draws, conversions) fills the deduction and brackets first, any deduction it leaves unused shelters gains, and gains are taxed by where they land in total taxable income. So adding ordinary income can push gains already realized that year into a higher LTCG bracket — which is why the year's taxes are computed from its final ordinary/gains totals (`TaxYear.OrdinaryTax` + `CapitalGainsTax`), not summed per step. A single sale is grossed up exactly by `TaxYear.GrossUpBrokerageSale` (piecewise-linear walk, like `GrossUpOrdinary`); the steps where ordinary income is added *after* gains are solved by `Bisection`. The 3.8% Net Investment Income Tax is not modeled, and gains don't change the (flat 85%) taxable share of Social Security. This requires tracking cost basis: a parallel `BrokerageBasis` scalar on `Accounts` runs alongside the `brokerage` balance, grown only by contributions (never by investment growth). Each year, `gainFraction = (brokerage - brokerageBasis) / brokerage` (clamped to `[0, 1]`) determines what fraction of that year's Brokerage withdrawal is taxable gain; the rest is a tax-free return of principal. `brokerageBasis` shrinks proportionally with the balance on withdrawal (`basis *= balanceAfter / balanceBefore`) to preserve the average-cost ratio for the following year. This is average-cost tracking, not per-lot/FIFO — there's a single running basis, not individual purchase records.
- `roth` withdrawals are never grossed up or taxed, regardless of the deduction.

Bracket thresholds are scaled by the same `InflationFactor` as the withdrawal and standard deduction (mirroring how the IRS itself inflation-adjusts brackets annually).

The per-year `RunYearDetail.TaxRate` (averaged per run as `RunSummary.AverageTaxRate`) is the blended effective rate across all three buckets — `totalTax / totalGrossWithdrawal`, where `totalTax` now includes both Taxable's bracket tax and Brokerage's LTCG tax (Roth always contributes 0, same as the old `nontaxable` bucket did). Each year's tax also breaks out into `OrdinaryTaxAmount` (Taxable's bracket tax, in dollars) and `CapitalGainsTaxAmount` (Brokerage's LTCG tax, in dollars) on `RunYearDetail`, surfaced separately in the web UI's per-year "Taxes" column. `CapitalGainsBracketRate`/`AmountUntilNextCapitalGainsBracket`/`NextCapitalGainsBracketRate` (from `TaxYear.CapitalGainsBracketRoom`) report the marginal LTCG bracket at the top of the year's income stack — the rate the next dollar of gain would face — including any harvested gains; `HarvestedGains` reports 0% harvesting (below). `RealizedGains` (the gain part of the year's Brokerage sales; the rest was basis) and `ZeroRateGains` (gains taxed at 0%) are reporting-only: the main page shows the Brokerage gain/basis split, and a superscript footnote - on the Roth conversion line, else the LTCG line - when the year's own sales filled the 0% band (realized gains at 0%, no room left, nothing harvested), explaining that more taxable income would push those gains to 15%. `TaxYear.BracketRoom` reports how many more gross Taxable-withdrawal dollars could be taken this year before crossing into the next ordinary bracket up (`AmountUntilNextBracket`) and what that next bracket's rate is (`NextBracketRate`, `null` once already in the top bracket) — it reuses `GrossUpOrdinary`'s accounting directly (the amount above the standard deduction maps 1:1 onto the inflation-scaled bracket thresholds) rather than re-deriving it.

**Age-gated withdrawals (the 59½ rule).** `Birthdate` (a `DateOnly`) and each model year's start date determine that year's age (`RetirementYear.AgeAtStart`, see the timeline above), and `ageEligible = AgeAtStart >= 59.5`. While `!ageEligible`: `taxable`'s pro-rata proportion is forced to 0 (no withdrawal from Tax Deferred at all), and `roth`'s *eligible* amount is `RothBasis` rather than the full `roth` balance (`Accounts.EligibleTaxable`/`EligibleRoth`) — mirroring `BrokerageBasis`, `RothBasis` is a parallel scalar seeded from `InitialRothBasis`, never grown by returns, and shrunk proportionally on withdrawal (`RothBasis *= balanceAfter / balanceBefore`), but (unlike Brokerage) never taxed regardless of eligibility — the age gate changes *how much* can be withdrawn from Roth, never *how* it's taxed. `brokerage` is never age-restricted. Once `ageEligible` is true, the eligible total equals the full `taxable + brokerage + roth` and every formula below reduces to exactly the unrestricted behavior. If the *eligible* total across all buckets can't cover a year's desired withdrawal — even while locked funds keep the full portfolio positive — the withdrawal is capped at what's eligible and the year fails, using the exact same failure machinery as a negative balance (see below).

**Withdrawal strategy** (`SimulationParameters.WithdrawalStrategy`, enum in `WithdrawalStrategy.cs`; **not a user input** — the web, Optimal page and console no longer offer a choice, and `/api/run`/`/api/optimal` ignore a `withdrawalStrategy` field). The Core default is **`Automatic`**: the Strategy Lab found neither order best for every household (with conversion tax paid out of the conversion, Pro-rata is within 0.5% of the best of six orders for 94.3% of households and Tax-optimized for 75.9%; the better of the two for 99.6%), so the app picks per household — together with how far to convert (`RothConversionTarget`, below). `AutomaticStrategy.Resolve` runs every candidate pair — {Tax-optimized, Pro-rata} × {12% fill, top of 22%, top of 24%, none}, or fewer when a choice is pinned or conversions are off — on 200 seeded paths (path *i* = `new Random(i)`) of the user's inputs at the requested spending and keeps the pair that survives more paths, ties going to more after-tax money left (`Accounts.AfterTaxValue`: Tax Deferred at 78%, Brokerage gains at 85%, so converting isn't penalized for paying tax early). `MonteCarloEngine.Run` resolves it before the iterations and reports the pair as `SimulationRunOutput.WithdrawalStrategy`/`RothConversionTarget` (the main page, Optimal page and console say which). The Optimal page (`SpendingOptimizer.BestCandidate`) uses a two-stage search per claiming age: the first candidate (Tax-optimized, 12% fill) gets a full break-even search, its 82.5% spend becomes the probe, every other pair is screened with one run per path at that spend (survivors, then after-tax money left), and the top `Finalists` (2) get full searches warm-started from the first candidate's break-evens; the highest 82.5% spend wins (`ClaimingAgeResult.WithdrawalStrategy`/`RothConversionTarget`). `WithdrawalStrategies.For(Automatic)` throws: it must be resolved first. Tests pin `ProRata`/`TaxOptimized` explicitly to exercise each order. Implemented by `ProRataWithdrawalStrategy` and `TaxOptimizedWithdrawalStrategy`. `ProRata` splits each year's net spending across the eligible buckets in proportion to their eligible balances. `ProRata` prices its Brokerage share's gains stacked on that year's Tax Deferred draw. `TaxOptimized` is **gains first** — it deliberately realizes gains while they're taxed at 0%: (1) Brokerage up to the sale whose gains fill the 0% band (`ZeroRateGainRoom`; unlimited for all-basis Brokerage, which realizes no gain), (2) Tax Deferred up to `TaxYear.OrdinaryFillCeiling` — the start of the 22% bracket, or lower if more ordinary income would push step 1's gains out of the 0% band, (3) more Brokerage at 15%/20%, (4) more Tax Deferred into the higher brackets — solved by `Bisection`, since that ordinary income pushes the year's realized gains up, (5) Roth as last resort. The 0% LTCG ceiling sits just $950 (un-inflated) below the 22% bracket, so in practice 0% gains take priority over 12%-bracket Tax Deferred income for the same room. The fill ceiling is a preference, not a hard cap — an earlier version treated it as a hard cap and failed runs with hundreds of thousands still in Tax Deferred once Brokerage and Roth ran dry. Each step is capped at what that bucket can *net* after tax (`TaxYear.BrokerageNetCapacity` for Brokerage), and the gross draws are clamped to their caps so float rounding can't leave a bucket at −1e-10 and falsely trip the negative-balance failure. In `TaxOptimized`, `IsShortfall` is "net need still unmet after every step", which is stricter than pro-rata's balance-vs-need check because it accounts for gross-up. The age gate still applies to both strategies via `EligibleTaxable`/`EligibleRoth` on `WithdrawalContext`. **Trade-off:** when the need is small, step 1 can cover it entirely from Brokerage, leaving that year's 10%/12% Tax Deferred room unused unless Roth conversions (web default on) fill it.

**0% gain harvesting** (`GainHarvest`; `TaxOptimized` only, via `IWithdrawalStrategy.HarvestsZeroRateGains`). After the year's withdrawals and conversion, any 0% room still left is used by selling and immediately rebuying Brokerage (the wash-sale rule only applies to losses): `BrokerageBasis` rises by the harvested gain, no cash moves, no tax is due, and future sales carry a smaller gain fraction.

**Roth conversions** (`RothConversion.Apply`; allowed via `SimulationParameters.EnableRothConversions` — the user's only conversion input, "Allow Roth conversions" on the web, C# default `false`, web checkbox default on). After each year's regular withdrawal, Tax Deferred money is converted to Roth up to a ceiling on total ordinary income (`grossTaxableWithdrawal + conversion`) set by `SimulationParameters.RothConversionTarget` (`RothConversionTarget.cs`; not a user input, default **`Automatic`** — the app picks it with the order, see Withdrawal strategy; `ConversionTargets.CeilingFor` maps each): `Bracket12` fills to `TaxYear.OrdinaryFillCeiling` — the inflation-scaled start of the first bracket at 22% or higher (`Bracket22CeilingGross`, read from the table, not hard-coded), or lower when that would push the year's already-realized 0% gains into 15%; `Bracket22`/`Bracket24` fill to the top of the 22%/24% bracket; `None` converts nothing. The Strategy Lab measured the pick: see Model Info. Years already past the ceiling convert nothing. Converting into the 22%/24% brackets after 63 raises Medicare IRMAA two years later, which the model charges (below), so the pick weighs it. The conversion's tax (`IncrementalOrdinaryTax` — `OrdinaryTax` on income with vs. without the conversion, the forward counterpart of `GrossUpOrdinary`) plus any extra capital gains tax it causes by stacking beneath the year's realized gains, is paid per `SimulationParameters.ConversionTaxFunding` (`ConversionTaxFunding.cs`; not a user input). The app's default is **`FromConversion`**: the tax comes out of the converted amount (`Withheld` — Tax Deferred falls by the full amount, Roth and `RothBasis` rise by amount minus tax; the same, dollar for dollar, as withholding from Tax Deferred or paying from Roth afterwards), so conversions never stall. The Strategy Lab's funding comparison chose it: it raised the 82.5% spend by +3.35% on average (95% interval +2.4% to +4.4%; about +30% for the 12% of households it helps, mostly early retirees whose Brokerage ran out) while lowering it by more than 0.5% in 6.2% of households — by −1.9% on average, where converting all the way to the line is slightly more than ideal and the old Brokerage cap held conversions back. The other rules: `Brokerage` (the original — paid by selling Brokerage through `GrossUpBrokerageSale`, so that sale incurs its own LTCG; if Brokerage can't cover the cost, `Bisection` finds the largest conversion it can fund, since the required sale rises with the amount converted), `BrokerageThenConversion` (Brokerage while it can pay, the rest withheld) and `BridgeAware` (like the latter, but before 59½ Brokerage keeps the spending still to come before the gate, which `RunSimulator.BridgeNeed` sums from the timeline). `RothConversion` splits its ordinary `Tax` between the sources (`OrdinaryTaxFromBrokerage`/`OrdinaryTaxFromConversion`, in proportion to each source's share of the cost); its `CapitalGainsTax` is the bump plus the funding sale's own gains tax. Converted dollars (net of any withheld tax) are added to both `roth` and `RothBasis`, so they're accessible anytime under the 59½ gate (the IRS 5-year seasoning rule isn't modeled); conversions themselves ignore the age gate since they aren't withdrawals. The year's reported `OrdinaryTaxAmount`, `CapitalGainsTaxAmount`, Brokerage withdrawal, blended tax rate, and bracket/room-to-next-bracket all include the conversion and its funding sale; `RothConversionAmount`/`RothConversionTax` break it out separately. **Who paid the ordinary tax** (reporting only; they sum to `OrdinaryTaxAmount`, which a component test checks every year): `SocialSecurityTax` (out of the benefit), `TaxDeferredWithdrawalTax` (withheld from the Tax Deferred draw — `WithdrawalPlan.TaxableTax`) and `RothConversionOrdinaryTaxFromBrokerage`/`…FromConversion`. The main page shows them in a superscript footnote on the Taxes column's ordinary-tax line — independent of the 0%-band footnote; `taxesBreakdown` numbers a cell's notes in the order they appear. `BracketRoom` assigns income sitting exactly on a threshold to the lower bracket, so a year that fills to the 22% line reads "12% bracket, $0 until 22%".

Two cash-flow features layer on top of that:
- **NewMoney** (a one-time inheritance) is credited directly into `brokerage` in its arrival year, increasing both the balance *and* the basis by the same amount — it's a cash contribution, not a gain, so it stays tax-free on arrival and isn't taxed later beyond its own subsequent growth.
- **Social Security** (`SocialSecurityYear`) is income in the year it's received, never deposited into any account. It starts on `SocialSecurityStartDate`, paid monthly, with a partial first year and inflation-indexed amounts (see the timeline above). A flat 85% of it (`TaxAssumptions.SsTaxableFraction`, a conservative simplification of the IRS provisional-income formula) is ordinary income, **stacked first** in the brackets: its own tax (`ssTax`) is computed at the lowest rates and the standard deduction, and every other ordinary income that year stacks on top of it. `GrossUpOrdinary` takes a `baseIncome` argument for exactly this — it starts from whatever deduction and bracket room Social Security left, and `baseIncome = 0` is the plain case. So the Tax-optimized 12% fill, the Roth-conversion room, `BracketRoom`, and `OrdinaryTaxAmount` (which includes `ssTax`) all net out the taxable Social Security. The after-tax benefit (`ss − ssTax`) reduces what the portfolio must supply that year (`need`); if it exceeds the year's spending, the surplus is saved into `brokerage` as basis (like NewMoney). Because it never touches `taxable`, Social Security is outside the 59½ gate, conversions, and the "% of balance" figure.
- **Medicare IRMAA** (`MedicareIrmaa`, tiers `FederalTaxBrackets.MedicareIrmaaSingle2026`): from the first of the 65th-birthday month (`RetirementYear.MedicareMonths`), each year pays the Part B + Part D income surcharge set by **MAGI from two years earlier** — 2026 single-filer tiers (above $109k / $137k / $171k / $205k / $500k: +$95.70 / $240.40 / $385.00 / $529.60 / $578.00 a month), thresholds and amounts scaled by the year's `InflationFactor`. MAGI (`RunYearDetail.Magi`) is the year's gross ordinary income (taxable Social Security, Tax Deferred draws, conversions) plus every realized gain, harvested gains included. The surcharge (`RunYearDetail.IrmaaSurcharge`, summed as `RunSummary.LifetimeIrmaaSurcharges`) is added to the year's spending need before Social Security nets against it, so it's paid like spending and can fail a run; it isn't counted as tax. It's why big conversions after 63 cost more than their income tax. The main page shows it in the Taxes column and the summary.

A run "fails" the instant `taxable`, `brokerage`, `roth`, or their combined total goes negative, *or* the eligible (currently-unlocked) total falls short of that year's desired withdrawal — a sub-account, or the age gate itself, can trigger failure even while the combined balance is still positive.

### Result shape

Everything is built from immutable records. `RunYearDetail` is one simulated year; `RunSummary` is one run — its `Years` (a failed run's list ends with the failure year) and `FailureYear`, with per-run stats (`EndingBalance`, `AverageAnnualReturn`, `AverageTaxRate`, `LifetimeTaxesPaid`, highest/lowest return and lowest balance) *derived* from `Years` rather than stored. `SimulationResult` is `Runs` plus aggregates derived from them (`OutOfMoneyCount`, and `YearsOutOfMoney`/`FailedScenarioAverages`, which cover failed runs only). `SimulationRunOutput` adds `AllRates`, the failure trace, and `LastSuccessfulRun`. To add a new per-year figure, add it to `RunYearDetail` and set it in `RunSimulator.SimulateYear`; a new per-run stat is usually just a derived property on `RunSummary`. These shapes are what `POST /api/run` returns as JSON (camelCase), so `app.js` reads `result.runs[i].years` and `output.lastSuccessfulRun`.

### Intentional quirks — not bugs

- `SuccessMoneyRemaining` holds one entry *per year*, not one ending balance per run — the balance of every year that didn't fail, across every run, including the pre-failure years of runs that later fail.
- The console's detailed "last run balances" report and the web's last-successful-run detail table only populate when **zero** iterations failed (`OutOfMoneyCount == 0`) — otherwise only the failure trace and per-run summary print.
- `gainFraction` (the fraction of a Brokerage withdrawal treated as taxable gain) is clamped to `[0, 1]`; an embedded loss in Brokerage (basis exceeding balance) never produces a tax rebate on withdrawal in this model.
- When Brokerage pays a conversion's tax (the `Brokerage`-first funding rules), a conversion that fills to the 0% ceiling leaves no 0% room for that sale's gains, so they're taxed at 15%.
- IRMAA: the first two years of retirement pay no surcharge — their lookback years are before the model starts, and SSA recalculates after a work stoppage (form SSA-44). Tiers are single-filer only (like the brackets), and the base Part B premium is treated as part of spending; only the surcharge is modeled.
- A run can fail in a year where its *total* balance (including age-locked Taxable and Roth-gains) is still comfortably positive — the age gate can make most of the portfolio inaccessible even while it exists on paper. This is the intended "early-retirement liquidity trap" behavior, not a display bug.

These were flagged during development and deliberately kept as-is; don't "fix" them without being asked.

### Non-determinism

`Random` is unseeded (`new Random()`) in the public `MonteCarloEngine.Run`, so real runs aren't reproducible. The engine no longer reads today's date — ages and inflation come from `Birthdate`, `RetirementDate` and the calendar — so the same parameters and seed give the same result on any day. Tests can pass a seeded `Random` to the `internal` overload — the engine-component refactor was verified that way, running old and new engines on the same seeds and requiring bit-identical output — and the components below the engine are deterministic, so `ComponentTests` asserts exact values. The verification approach used throughout this repo's history is structural/cross-referential instead: e.g., confirming a run's reported highest/lowest return year matches the max/min line in that same run's own printed trace, or confirming a value that should compound (like NewMoney) actually persists into the following year rather than reverting.
